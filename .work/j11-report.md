### 6. Unpublished and non-public records never appear

An allow-list, not a filter. Two independent barriers, one per half:

- **Unpublished** — `eq(pages.status, "published")` and `eq(posts.status, "published")` are in the
  SQL `WHERE`, so a draft is never fetched, never scored, never counted in `total`.
- **Non-public** — `inArray(posts.contentType, PUBLIC_POST_TYPES)`. `PUBLIC_POST_TYPES` is derived
  at module load from the two maps the route resolver itself uses: a type is searchable only if a
  `COLLECTIONS` prefix exists for it **and** it is absent from `NON_PUBLIC_CONTENT_TYPES`. It
  resolves to `news, story, video, album, publication, job`. A new internal content type is
  invisible to search the day it is added, without anyone remembering to add it here.

**Unpublished, demonstrated.** `kape.db` has no draft rows at all — every page and post is
`published` — so the criterion was not demonstrable against seeded data. I inserted three fixtures
into the **scratch copy only**, all carrying the token `Zarquon`: a published page (the control), a
draft page, and a draft news post.

```

pages|37|j11-probe-draft|draft
posts|27|j11-probe-draft-news|draft

q="Zarquon" lang=en total=1 limit=30 shown=1
  [12] page/Page /j11-probe-published — Zarquon probe published page
```

One result, not three. The control proves the token itself is findable, so the two absences are the
status filter and not a broken query. `kape.db` still reports 35 pages and 26 posts.

**Non-public, demonstrated.** `kape.db` has two `document` posts (23 `5-Year Strategic Plan`, 24
`Procurement Guidelines`), both `published`, plus 2 `internal_news`, 3 `event` and 2 `announcement`.

```

q="លទ្ធកម្ម"      lang=km → total=0
```

exactly. `document` is the content type the staff portal serves at `/internalsources/documents`;
`repo/staff.ts:70` reads it behind `staffProcedure`, and it must not leak to the public site.

### 7. The query is parameterised

The only place a reader's string reaches SQL, `src/server/repo/search.ts:86-94`:

```ts
/** `%` and `_` are LIKE wildcards; a reader typing them means the characters. */
const escapeLike = (s: string) => s.replace(/[\\%_]/g, (c) => `\\${c}`);

/**
 * The one place a query string reaches SQL. `${translations.value}` is a column
 * reference and the pattern is a bound parameter — Drizzle never inlines it.
 */
const containsQuery = (query: string) =>
	sql`${translations.value} LIKE ${`%${escapeLike(query)}%`} ESCAPE '\\'`;
```

`containsQuery(query)` is called once and the resulting `SQL` object is reused as `match` in all
three `.where(and(…))` clauses. Every other predicate is `eq`/`inArray` over a column and a
constant. There is no string concatenation into SQL anywhere in the module.

In Drizzle's `sql` template a column object interpolates as an identifier and a JavaScript string
interpolates as a bound `?` parameter, so the pattern never becomes SQL text. The `ESCAPE '\'`
clause is literal SQL, not user input.

Probed:

```
q="' OR 1=1 --"              → total=0
q="x'; DROP TABLE pages; --" → total=0
select count(*) from pages   → 37   (unchanged)
```

The wildcard escaping is a correctness fix rather than a security one, but it is worth checking
because without it `%` matches every row:

```
q="%" → total=0
q="_" → total=0
```

### 8. Results are capped

**Capped, not paginated. Limit 30**, `SEARCH_LIMIT` in `search.ts:27`, overridable per call via the
fourth argument. `total` is the full match count before the cap, so the page can say what it is
withholding rather than silently truncating:

```
q="e" lang=en total=68 limit=30 shown=30
```

and renders `68 results — showing the first 30`. Paging was not worth it: the whole site is a few
hundred rows and no realistic query exceeds 30 without being meaningless.

### 9. A runnable test covering ranking and filtering

`src/server/repo/search.test.ts`, 7 tests, no database — `searchSite` takes `db` as a parameter and
the scoring logic is pure, so the tests import nothing that pulls in `bun:sqlite` and run under
vitest unchanged.

Ranking:
- title match > excerpt match > body match, for the same word
- exact title > title-initial > title-buried
- Khmer scores like English

Filtering:
- **a body hit that only matched the JSON scaffolding scores 0.** `body` is stored as ProseMirror
  JSON, so a raw `LIKE` also matches node names and attribute keys — searching `paragraph` would
  otherwise return every record on the site. Each candidate is re-checked against the text
  extracted from the JSON before it counts. Confirmed live: `q="paragraph"` → `total=0`.
- Khmer body text is read back out of the stored JSON correctly
- **no member of `PUBLIC_POST_TYPES` is in `NON_PUBLIC_CONTENT_TYPES`**, and `document` and
  `internal_news` are specifically absent. This is criterion 6's boundary as a runnable check — if
  someone adds `document` to `COLLECTIONS`, this test fails before the leak ships.

Plus one snippet test (the excerpt centres on the match rather than always starting at the top).

## Two things the contract got wrong

Both are places where I did more than the contract said, in files I own. Flagging them because a
reviewer diffing against the contract will notice.

### The header default alone does not bring the link back

The contract says pointing `header_search_link` at `/search` in `header-defaults.ts` makes the link
return "on its own". It does not, on any database that has already been seeded.
`HEADER_DEFAULTS` is read in exactly two places: `seed/site.ts:20`, which inserts it once, and
`admin.nav.tsx:34`, which uses it as a form placeholder. The Header itself never consults it — it
reads `site_settings` straight from the DB, and `kape.db` holds

```
header_search_link|/sitemap.xml
```

seeded before search existed. So on the real database `isPageHref("/sitemap.xml")` is false,
`showSearch` is false, and the link stays hidden no matter what the defaults file says. Only a fresh
`db:seed` would pick the new value up.

The fix is four lines in the entry point I own, and it does **not** weaken the predicate — it uses
it:

```ts
// a labelled control must not hand a reader a machine file (/sitemap.xml)
const isPageHref = (h?: string) => !!h && !/\.[a-z0-9]+(?:[?#]|$)/i.test(h);
// A stored search link that is a file (the pre-search /sitemap.xml default) is
// not a search destination, so fall through to the real one.
const searchLink = isPageHref(settings.header_search_link)
	? settings.header_search_link
	: HEADER_DEFAULTS.header_search_link;
const searchHref = withLang(searchLink, lang);
```

`isPageHref` is unchanged and still guards the final href; the `isPageHref(...)` term dropped out of
`showSearch` only because `searchLink` is now guaranteed to satisfy it. `showSitemap` is untouched.

Confirmed live against the scratch copy of `kape.db`, whose setting still reads `/sitemap.xml`:

```
Array.from(document.querySelectorAll('a')).filter(a => /ស្វែងរក|Search/.test(a.textContent))
  .map(a => a.textContent.trim() + ' -> ' + a.getAttribute('href'))

on /en → ["Search -> /en/search"]
on /km → ["ស្វែងរក -> /km/search"]
```

Clicking it from `/km` lands on `/km/search` with H1 `ស្វែងរក`.

If you would rather the data were correct than the code defensive, the alternative is one statement
and my Header change can be reverted:

```sql
UPDATE site_settings SET value = '/search'
 WHERE tenant_id = 1 AND key = 'header_search_link';
```

I did not run it. It is a write to `kape.db` and that is the orchestrator's call, not a worker's.
My preference is to keep the code change regardless: it also covers the key being unset, which is
what the comment at the top of `header-defaults.ts` already promises and what `admin.nav.tsx`
already does.

*(Harness note, not a defect: `agent-browser click` on that anchor reported success without
navigating; `element.click()` in `eval` navigated correctly. Same class of thing as the documented
`press Enter` bug. Keyboard submit on the search form was proved with `press Space` as instructed
and works — it produced `/km/search?q=ជំនាន់ថ្មី`.)*

### The route needs a server call, and I do not own the tRPC router

Every other route in this app fetches through `context.trpc.*`, which would mean adding a `search`
procedure to `src/integrations/trpc/router.ts`. That file is not in my contract, and the backlog
rule is explicit: a job that needs a file it does not own stops and reports, it does not reach
across. J21 owned it last and is committed, so nothing would have collided — but "uncontended" is
not "mine".

So the server call is a `createServerFn` inside my own route file:

```ts
const runSearch = createServerFn({ method: "GET" })
	.validator((input: { q: string; lang: string }) => ({
		q: String(input.q ?? ""),
		lang: String(input.lang ?? DEFAULT_LANG),
	}))
	.handler(({ data }) => searchSite(db, data.q, data.lang));
```

This is a first-class TanStack Start primitive, not a workaround — `@tanstack/react-start` is
already a dependency, and it is the framework's own answer to "a route needs server data". It is
also strictly better here than tRPC would have been: it sidesteps the SSR self-fetch entirely, so
this route cannot hit the `PORT`-mismatch whole-page 500 that the contract warns about.

I verified the compiler really does split it, because if it did not, `bun:sqlite` would land in the
browser bundle:

```
bun run build → exit 0
grep -rl "bun:sqlite" dist/client/                        → no matches
grep -rl "searchSite\|drizzle" dist/client/assets/*.js    → no matches
dist/client/assets/_lang.search-D-I-_Jwp.js               → exists
```

The route's client chunk is built and contains none of the server module. No console errors and no
page errors on a real hydrated load.

Converting to tRPC later is mechanical if you prefer the convention: move the two lines into a
`search` router and swap the loader to `context.queryClient.ensureQueryData(context.trpc.search…)`.
`searchSite(db, q, lang)` is already shaped like every other repo function and needs no change.

## Design notes

- **No FTS5, and it was not close.** A parameterised `LIKE` over `translations` handles a 466-row
  table in a single indexed-scan-free pass; the slowest probe (`q="e"`, 68 matches across three
  entity types) returned instantly. Per the stop condition I did not generate a migration, and the
  lane stays at `0016`.
- **SQL narrows, JavaScript ranks.** Ranking in SQL would have meant either a `CASE` ladder or
  scoring the JSON bodies in SQLite, and it could not have done the JSON-scaffolding recheck at all.
- **Scoring.** `title`/`name` 6, `excerpt`/`summary` 3, `body` 1; ×4 exact, ×2 leading, ×1 buried;
  summed across the fields a record matched in, max per field so a record matching in both languages
  is not double-counted. Ties break on title, so ordering is stable.
- **Sub-project hrefs nest.** `/projects/<parent>/<slug>`, via a self-join alias mirroring
  `route.ts:56-75`. `kape.db` has no sub-projects yet, so I proved it by temporarily parenting
  `ngprc` to `ngs` in the scratch copy — `q="Pedagogical"` returned `/projects/ngs/ngprc` — then
  reverted it (`select count(*) from projects where parent_id is not null` → 0).
- **`robots: noindex`** on the results page, matching `$lang.donate.success.tsx`. A search results
  page is not content and should not be indexed.
- **Not searched:** `people` (the team collection) and media captions. Neither is in scope and
  neither has the title/excerpt/body shape the module assumes. Say the word and `people` is ~15
  lines.
