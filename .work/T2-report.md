## Decisions the contract left open

**The procedures live on `adminSettings`, not on a router of their own.** `adminProcedure` resolves
the permission area from the first segment of the tRPC path, through `ROUTER_AREA` in
`src/lib/permissions.ts`. A new `adminUiStrings` key is absent from that map, and an unmapped admin
router defaults to deny for everyone who is not a super admin. The contract says the area is
`settings` and forbids a new permission key, and `adminSettings` is already mapped to `settings`, so
the three procedures hang off it: `adminSettings.uiStrings`, `.setUiString`, `.resetUiString`. Same
guard, same area, no second pattern, and no edit to a file I do not own.

**"Overridden" means "reads differently from the default", not "has a row".** The installer writes
every shipped default into `ui_strings` at install time, so a stored row is not by itself a change.
Reading it as one would have put the filter and the Reset button on all 253 keys and told the
operator nothing. On the KAPE database the filter reports 83 of 333 keys changed, which is the
honest number.

**The placeholder falls back across languages.** A key with an `en` default and no `km` one shows
the `en` default as the `km` placeholder, because that is what the site actually renders in Khmer
through the per-key fallback in `getUiStrings`.

**Enter in a field saves the row.** Tabbing from a field lands on the next language, not on Save, so
without it a keyboard save is two tabs and a space. `admin.settings.tsx` already binds Enter this
way in its Add setting row.

## Cache

Nothing needed invalidating beyond what the platform already does, and I checked rather than assumed.

- The strings reach a visitor through the root loader, which calls `i18n.bootstrap` -> `bootstrapI18n`
  -> `getUiStrings`. That reads the table on every SSR request and holds no cache of its own.
- The only server-side cache in the path is the incremental-SSG render cache, and `adminProcedure`
  already clears it after every admin mutation (`src/integrations/trpc/init.ts:77`). My three
  procedures are `adminProcedure`, so a save clears it for free.
- Proof, not inference: the visitor screenshots below were taken in a fresh browser context, with no
  admin cookie and no warm client cache, against the same never-restarted dev server, before and
  after the save.

## Blocker

`/admin/ui-strings` has no entry in `NAV_AREA`, so `canSee` in the admin shell shows the sidebar item
to every admin user whatever their role. The server still refuses them - the procedures answer to
`settings` - but they would see a screen that then failed to load, and `modules.test.ts` fails on
exactly this. The fix is one line in `src/lib/permissions.ts` and one in `src/lib/modules.ts`,
neither of which this job owns, so I stopped at that line.

```sh
cd /home/userx/workspace/kape && \
perl -0pi -e 's{\t"/admin/languages": "settings",}{\t"/admin/languages": "settings",\n\t"/admin/ui-strings": "settings",}' src/lib/permissions.ts && \
perl -0pi -e 's{\t"/admin/languages",}{\t"/admin/languages",\n\t"/admin/ui-strings",}' src/lib/modules.ts && \
bun run test
```

That takes `modules.test.ts` green. `no-brand.test.ts` is the other pane's to close.
